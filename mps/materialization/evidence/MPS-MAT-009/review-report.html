2The acceptance claim, reconstructed by the reviewer

Stripped of narrative, the Stage A package asserts a chain in which each link is a separate proposition and any one of them failing breaks the warrant:

  • P1 — Structural integrity. Nine languages, 96 uniquely owned concepts, an acyclic dependency graph with declared kinds, projections that own no authority, and 119 imported HLR roots confined to the import model.
  • P2 — Corpus fidelity. The MPS model says what the controlled document says, per record and per field, over all 119 requirements.
  • P3 — Reproducible generation. The project builds headless from a genuinely clean state, outside the IDE, idempotently, without mutating authored persistence.
  • P4 — Semantic enforcement. Generation is not checking, so a separate mechanism (native launchtests) demonstrates that a checking rule actually fires; and it is shown to be capable of going red, and red for the right rule.
  • P5 — Evidence currency and portability. Both verdicts are bound to the tree they were taken on, and every referenced artifact is obtainable and hash-verifiable from a fresh clone.
  • P6 — Complete acceptance bookkeeping. Every acceptance item marked complete carries attributable evidence for what its own freeze declares required; every deferral that has outlived its justification has been reclassified and discharged.
  • P7 — MPS-MAT-009's own item text. No patient data, no credentials, no signing keys, no authority cutover.

The package's declared self-check is .github/workflows/controlled-spec-gates.yml, and CLAUDE.md requires every step in it to be run before a commit that closes a checkpoint. That workflow is therefore itself part of the acceptance claim, not merely a convenience.

5Attacks that did not expose a defect

These are recorded because a review that lists only its hits is not a measurement. Each was a genuine attempt to break a claim; each claim held.

The cold build clause — held, and independently confirmed.

The clone was observed to have zero source_gen/classes_gen/test_gen directories and no build/work/ before anything ran, so coldness was established by the reviewer rather than taken from the record. Build: exit 0 in 50s over all 12 modules, git status over the project empty afterwards. Second independent build over that output: exit 0 in 33s, still clean. This is a stronger result than the package's own, because F3 shows the package could not have established the premise.

The model-test clause — held.

Reconstructed launchtests invocation, run from a fresh process: tests="2" skipped="0" failures="0" errors="0", both identities present (test_S1_…REA_C_002… and test_testAssessedClaimWithoutEvidenceIsRejected). The recorded authored = discovered = executed = 2 is a true statement about this tree.

The retained control patches are implementer assertions — refuted.

Both patches were applied to the base tree and the resulting model-tree hash compared to the recorded perturbed_model_tree_sha256. Both reproduce exactly: df52b5e1… for failure sensitivity and 2308bbb6… for foreign-rule discrimination. Reversing each returns to 7a7f2362…. The patch_reproduces_perturbed_tree flag, which the gate only checks for truthiness, is true in fact.

Failure sensitivity rests on narrative — refuted, by re-execution.

Applied the perturbation, rebuilt cold, and re-ran the tests. Result: tests=2, failures=0, errors=1, BUILD FAILED, exit 1, with S1 not passing and H1 passing — and the assertion text matches the recorded one character for character: java.lang.AssertionError: node <VerificationClaim [1365532761392382826]> does not have the expected 'error' message ''. This is the package's strongest claim and it survives independent execution.

The currency key omits the test model — refuted.

Hypothesis: if nltps.modeltests lived outside PROJECT_DIR, editing the tests would not invalidate the verdicts. It does not — the test module is registered in the project's own modules.xml under $PROJECT_DIR$/tests/ and is inside the hashed population.

Patient data, credentials, signing keys, authority cutover — not found.

Direct scan of the persisted corpus (122 documents, 651,648 bytes) for private-key and certificate blocks, password/secret/token assignments, bearer tokens, AWS keys, MRN and patient-identifier fields, dates of birth, email addresses and phone numbers: zero hits in every category. All 119 exported records carry authoritative: false and lifecycle_state: "proposed"; the persisted corpus contains no value="true" property at all. Every occurrence of “signed”, “approved” and “release” is inside requirement statement text, never a state assertion. MPS-MAT-009's literal item text verifies.

The concept ceiling can be driven down by file-per-root conversion — refuted.

check_module_graph.py globs */models/*.structure.mps without going through mps_layout, and its only count assertion is an upper bound (total_concepts > max_concepts), so a silent under-count looked reachable via the project's own declared default persistence. Converting a language structure aspect to folder form was caught: - languages without a structure aspect: ['nltps.roles.therapy']. The protection comes from an aspect-presence check rather than from the count, but it is real.

The neutral export could be stale against the model — refuted.

Perturbing the export alone is caught by both export_hlr_corpus.py --check and the equivalence gate; perturbing the model alone is caught by the exporter. The exporter genuinely reads the persisted model and never reads the bundle, so the two sides of the Stage-B comparison are independent as claimed. (What is not as claimed is which instrument carries the binding — see F5.)

6Limitations of this review

L1 — No model-aware route.

No MPS IDE session was attached to this clone, so the mps_mcp_* toolkit was unavailable. Anything requiring a live model write — most importantly running the GOV-C-004 literal example in F2 — could not be attempted. F2 is therefore a finding about the acceptance record, not a claim that the constraint is wrong.

L2 — Single host.

All executions ran on the same machine that produced the original evidence (hostname HUPCI-LAP-11 appears in both). Host-independence of the build and test results is untested; a second machine would be required.

L3 — Structural only.

Nothing here speaks to clinical correctness, risk acceptability, or whether REA-C-002 is the right condition. Verifying that the model faithfully mirrors the document says nothing about whether the document is right.

L4 — Areas probed shallowly or not at all.

The role-ontology gate, the model-persistence gate, the trace graph and risk register, the four projection languages' semantics, and the provenance of the 119 records against the source LaTeX document were read but not adversarially attacked. The document-build CI job was not run. Absence of findings in these areas is absence of evidence.

L5 — One negative control was itself invalid and was discarded.

The first attempt to bisect F1 extracted each commit with git archive; with no .git present the gate raised fatal: not a git repository and returned non-zero at every commit, including known-good ones. That is a measurement failure that reads exactly like a finding. It was re-run with real clones before any conclusion was drawn, and is recorded here because the same trap is available to the next reviewer.

7Disposition

FAIL

Not INVALID / INCOMPLETE: every measurement reported above was established as applying to the intended object, population and environment, and the two defects are reproducible from the commands given.

The warrant fails on two independent grounds, both in the evidence and bookkeeping layer rather than in the modelled system:

  • F1 — the commit offered for review does not pass its own declared gate suite, and has not since the first commit of this evidence package. The acceptance procedure's own precondition is unmet.
  • F2 — MPS-MAT-005D is recorded complete while evidence its own freeze declares required is absent from the controlled record, its deferral still reads “Required, not demonstrated”, and no gate examines that deferral class or reconciles evidence_required at all. This violates the project's own acceptance rule and is the precise failure the project predicted for itself in writing.

Set against that, the technically hardest claims in the package held under adversarial execution and are stronger than the record itself could establish: the cold build reproduced on a tree whose coldness the reviewer verified directly, the model tests reproduced at 2/2 with both identities, and both red-state controls reproduced — hashes byte-exact and, for failure sensitivity, the assertion text character-for-character. F3–F7 are measurement-path defects that do not falsify P1–P5 but do mean several instruments credit themselves with discriminations performed elsewhere or not at all.

Recommended sequencing, for whoever holds the repair authority: F1 and F2 are acceptance-blocking and F1 carries a design decision (the hygiene/currency control conflict) that should be resolved deliberately rather than by whichever gate is edited first. F3 and F5 are the highest-value non-blocking repairs, because each converts an assertion into an observation. F2's gate gap — no literal_example_substitution branch, no evidence_required reconciliation — is worth more than the single missing demonstration, since it is what allowed the omission to be invisible.
