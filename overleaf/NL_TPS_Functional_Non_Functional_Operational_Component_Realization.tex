\NLFrontMatterSection{Executive summary}

This specification defines 78 category-scoped component responsibilities: 32 functional, 23 safety and assurance, and 23 operational. It then maps all 357 categorized sub-requirements to the complete components and team-of-teams participation needed for realization.

A component in this document is an accountable realization responsibility, not necessarily a separately deployed software service. One deployed service may implement several responsibilities, and one responsibility may span software, configuration, procedures, evidence, and people. Consolidation is permitted only when interfaces, independence, human authority, verification, and separation-of-duties obligations remain demonstrably satisfied.

\begin{nlnotice}{EXISTING TPS AND DICOM BOUNDARY}
The NL-TPS shall integrate with commissioned treatment-planning systems through verified DICOM/DICOM-RT exchange at minimum. A vendor API may supplement that boundary only when separately approved and validated. The NL-TPS does not silently replace TPS calculation, commissioning, professional review, independent QA, plan approval, transfer verification, or delivery authority.
\end{nlnotice}

\section{Realization model}

Each category uses a mandatory universal stack plus direct components selected by the sub-requirement's domain, legacy allocation, and exact obligation. The allocation table lists the complete component set, not merely a suggested subsystem. The accountable team coordinates the realization; partners supply required specialist work and evidence.

\begin{itemize}
\item \textbf{Functional realization} implements patient-specific and user-visible planning capabilities, governed data transformation, inference, review, and existing-TPS exchange.
\item \textbf{Safety / assurance realization} implements cross-cutting safety, human-factors, privacy, security, integrity, and assurance constraints.
\item \textbf{Operational realization} implements institutional governance, deployment, monitoring, resilience, commissioning, release, change, and continued-authorization controls.
\end{itemize}

\section{Required realization packages and definition of done}

Each allocated component shall provide, as applicable: an approved owner and intended responsibility; architecture and interface contracts; threat, hazard, privacy, and use-risk inputs; controlled configuration; build and dependency identity; data dictionary and provenance behavior; failure and degraded-mode behavior; monitoring and alert rules; operating and support procedures; unit and component tests; integration and negative tests; trace to verification results; known limitations; anomaly disposition; commissioning evidence; and release approval.

The external TPS package shall additionally contain the site- and version-specific DICOM conformance assessment; application entities, roles, SOP classes, transfer syntaxes, and security profile; DICOM-RT object and attribute mapping; UID, reference, frame, geometry, unit, dose-basis, approval-state, completeness, and private-attribute rules; import/export and round-trip tests; optional vendor-API contract; reconciliation behavior; downtime procedure; commissioning results; supported-use matrix; and known limitations.

A sub-requirement is complete only when every allocated component has supplied acceptable evidence and the integrated workflow verifies the parent intent. No component, model, interface, or team can self-approve the clinical release when independence or governance rules require another role.
