\NLFrontMatterSection{Executive summary}

This specification derives a controlled interface baseline from all 111 NL-TPS high-level requirements. Each parent has three interface children: a controlled contract requirement, a runtime interaction and failure-behavior requirement, and an evidence and conformance requirement. The resulting 333 requirements define what must cross system and team boundaries before detailed interface-control documents, software contracts, DICOM conformance statements, vendor integrations, and commissioning protocols are completed.

The NL-TPS is a team-of-teams system that coordinates clinical users, deterministic safety controls, evidence services, imaging and planning services, inference models, data and audit services, quality and release controls, operations, and commissioned external systems. Existing TPS platforms remain authoritative within their commissioned roles. DICOM and DICOM-RT are the minimum portable external exchange foundation; approved vendor APIs, IHE-RO profiles, FHIR, or CodeX exchanges may supplement but shall not silently replace the commissioned DICOM route or bypass human approval and independent QA.

\section{1. Purpose, scope, and derivation}
The controlled trace path addressed by this specification is:
\begin{center}
\textbf{ConOps} $\rightarrow$ \textbf{high-level requirements} $\rightarrow$ \textbf{high-level interface requirements} $\rightarrow$ \textbf{ICDs, conformance statements, APIs, tests, and commissioning evidence}
\end{center}
The interface requirements are parallel refinements of the high-level requirements. They do not replace the detailed functional sub-requirements or component allocations. A parent is interface-complete only when all three children and every assigned interface family are implemented and verified together with the parent requirement.

\section{2. Requirement conventions}
Interface requirement identifiers use \texttt{IF-<parent>-<child>}. The suffix has the following controlled meaning:
\begin{itemize}
\item \texttt{-01}: interface-control baseline, actors, authority, direction, schemas, semantics, versions, states, security, errors, and ownership;
\item \texttt{-02}: runtime validation, authorization, safety behavior, state transition, negative paths, degradation, and explicit outcomes;
\item \texttt{-03}: traceability, conformance, verification, interoperability, commissioning, monitoring, anomaly, and release evidence.
\end{itemize}
The words \textit{shall}, \textit{should}, and \textit{may} are interpreted as mandatory, recommended, and permitted, respectively. Interface families identify logical boundaries, not a mandated deployment topology or procurement decision.

\section{3. Interface architecture and standards baseline}
Every interface-control document shall identify producing and consuming actors; authority and trust boundaries; direction and trigger; synchronous, asynchronous, or human interaction mode; message, object, or event model; required and conditional content; identifiers and references; terminology, units, coordinates, and rounding; state and approval semantics; version negotiation; security and privacy; timing, idempotency, retry, timeout, and cancellation; errors and degraded behavior; audit and provenance; monitoring; ownership; and acceptance evidence.

The current planning baseline is \href{https://dicom.nema.org/medical/dicom/current/output/chtml/part01/sect_1.2.html}{DICOM PS3.1 current edition}, \href{https://dicom.nema.org/medical/dicom/current/output/html/part02.html}{DICOM PS3.2 Conformance}, \href{https://dicom.nema.org/medical/dicom/current/output/chtml/part01/sect_6.4.html}{DICOM PS3.4 Service Class Specifications}, \href{https://dicom.nema.org/medical/dicom/current/output/html/part15.html}{DICOM PS3.15 Security and System Management Profiles}, and the \href{https://profiles.ihe.net/RO/index.html}{IHE Radiation Oncology Technical Framework, Revision 4.0}. DICOM facilitates multi-vendor exchange but does not by itself guarantee interoperability; each vendor, version, site, machine, modality, technique, and workflow therefore requires paired conformance analysis, controlled object and transaction scope, negative and round-trip tests, reconciliation, and commissioning.

\section{7. External TPS and DICOM interface baseline}
For every commissioned external TPS connection, T-INT with T-PLAN, T-IMG, T-REV, T-DATA, T-SEC, T-OPS, T-VV, representative clinical users, and the vendor shall establish an interface-control and commissioning package containing:
\begin{itemize}
\item application entities, real-world activities, initiators and responders, network services, DICOMweb services where used, SOP Classes, SCU and SCP roles, transfer syntaxes, security profiles, association behavior, timeouts, retries, and destination acknowledgment;
\item an approved object and transaction allowlist covering applicable image, registration, segmentation or structure, RT Plan, RT Ion Plan, RT Dose, treatment-record, and second-generation radiotherapy content;
\item patient, study, series, SOP Instance, and Frame of Reference UID rules; reference-graph integrity; coordinate transforms; geometry; nomenclature; units; dose basis; plan and approval states; and source-to-destination fidelity;
\item import, export, query/retrieve, storage, duplicate, orphan, stale, partial-transfer, timeout, rejection, retry, rollback, round-trip, and reconciliation behavior;
\item paired DICOM conformance statements and a documented gap analysis, including private attributes, unsupported or lossy semantics, vendor-specific limitations, and mitigations;
\item a bounded optional vendor-API contract, if approved, that identifies authentication, authority, schema, version policy, monitoring, validation, and fallback to the DICOM route without granting treatment-delivery authority; and
\item site acceptance, commissioning, independent review, representative and boundary cases, known limitations, change triggers, regression, monitoring, incident handling, rollback, support, and release evidence.
\end{itemize}

\section{8. Interface definition of done}

\begin{itemize}
\item parent, hazard, interface, component, test, result, anomaly, monitoring, and release trace with accountable owners;
\item approved interface-control document and machine-readable schema or object profile with examples and controlled terminology;
\item implemented positive, negative, boundary, wrong-patient, wrong-context, stale-version, timeout, retry, cancellation, partial-failure, rollback, recovery, and adversarial behaviors;
\item security, privacy, performance, availability, audit, provenance, retention, monitoring, support, and change responsibilities;
\item producer, consumer, integrated, interoperability, human-factors where applicable, commissioning, and acceptance evidence; and
\item clinical, physics, dosimetry, quality, systems, interoperability, cybersecurity, operations, and independent V\&V approvals required by the release gate.
\end{itemize}

\section{10. Controlled open interface decisions}
The following deployment-specific decisions shall remain controlled until resolved through architecture, clinical governance, interface control, vendor coordination, cybersecurity, commissioning, and change control:
\begin{itemize}
\item deployed producers, consumers, endpoints, protocols, schemas, events, topology, network zones, hosting, performance, availability, and service levels;
\item exact external TPS vendors, versions, application entities, SOP Classes, roles, transfer syntaxes, DICOMweb services, IHE-RO profiles, private attributes, and optional APIs;
\item disease-site, modality, technique, machine, dose, robustness, contour, registration, and workflow data semantics that are not portably represented across systems;
\item terminology, nomenclature, units, coordinate transforms, rounding, approval-state mappings, and conflict resolution;
\item authentication federation, certificate and secret management, encryption, audit transport, egress, data residency, retention, privacy, and incident coordination;
\item version negotiation, backward compatibility, migration, timeout, retry, idempotency, cancellation, rollback, downtime, recovery, and reconciliation; and
\item final ownership, supplier responsibility, support, change notification, acceptance criteria, tolerances, monitoring thresholds, and release evidence.
\end{itemize}
\textbf{Bottom line. }No high-level NL-TPS capability is complete at a team or system boundary until its interface contract, runtime behavior, evidence, and commissioned external-system route are all approved and traceable.
